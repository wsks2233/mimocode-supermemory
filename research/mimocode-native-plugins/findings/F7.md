# F7: Practitioner failures & counterexamples when wiring coding-agent plugins / MCP / memory (supermemory, opencode-supermemory, MiMoCode)

## Findings

### [1] opencode-supermemory@2.0.13 treats failed model-limit metadata as a hard-coded 200K window, so large-context models (~1M) get plugin-initiated compaction at ~160K tokens.
- quote: "In `opencode-supermemory@2.0.13`, a failed initial model-limit lookup causes proactive compaction to use a hard-coded 200,000-token context window. With the default `compactionThreshold: 0.8`, a model advertising a ~1M context window can consequently be compacted at ~160K tokens"
- url: https://github.com/supermemoryai/opencode-supermemory/issues/85
- source_type: primary
- published: 2026-09-13
- confidence: high

### [2] opencode-supermemory has no reliable opt-out for plugin compaction: threshold 0 is silently restored to 0.8, threshold 1 still fires on empty cache, and host `compaction.auto=false` does not stop plugin `session.summarize()`.
- quote: "Setting `compactionThreshold: 1` is **not** a reliable workaround for this failure: an empty cache still causes compaction at 200K. Setting it to 0 is also not an opt-out; validation restores 0.8. Disabling host `compaction.auto` does not prevent the plugin from explicitly requesting summarization."
- url: https://github.com/supermemoryai/opencode-supermemory/issues/85
- source_type: primary
- published: 2026-09-13
- confidence: high

### [3] A community report on opencode-supermemory documents three compaction bugs at once: post-summarize "Continue" sticks the session on the wrong (compaction) model, summarize can overflow a smaller compaction model, and the plugin races OpenCode's native `compaction.auto`.
- quote: "On a non-Claude provider whose compaction model has a smaller context window than the main model, the plugin's custom compaction path (a) overflows the compaction model, (b) leaves the session \"stuck\" on the compaction model after summarizing, and (c) races with OpenCode's native `compaction.auto`."
- url: https://github.com/supermemoryai/opencode-supermemory/issues/69
- source_type: primary
- published: 2026-08-11
- confidence: high

### [4] The same opencode-supermemory report shows production evidence of large sessions (47 sessions >1M tokens and 104 >200K in a 13-day window) and a feature gap: memory capture is post-hoc lossy summary only, with no pre-compaction extraction.
- quote: "In a 13-day window I see **47 sessions >1M tokens and 104 >200K** in `~/.local/share/opencode/session.db`… The only memory captured is the lossy post-compaction summary (`saveSummaryAsMemory`…). There is no pre-compaction extraction step."
- url: https://github.com/supermemoryai/opencode-supermemory/issues/69
- source_type: primary
- published: 2026-08-11
- confidence: high

### [5] Supermemory's official MCP engineering post admits its no-auth URL-as-key design has security and durability drawbacks: clearing cookies loses all memories, and anyone who obtains the nanoid URL can access them.
- quote: "There are obviously some huge drawbacks to this approach: - If the user clears the cookies, they will lose their memories - If anyone finds out the URL for the user, they might be able to access it."
- url: https://supermemory.ai/blog/the-ux-and-technicalities-of-awesome-mcps/
- source_type: primary
- published: 2025-06-08
- confidence: high

### [6] Supermemory documented that early MCP clients (notably Claude) mis-handled their memory MCP by preferring resources over tools, requiring an "unhinged" prompt to force correct tool use; long-lived SSE also caused constant "Connection lost" complaints until Cloudflare durable objects.
- quote: "when we launched, the MCP didn't work on Claude because it really wanted to use a resource instead of a tool. Which meant that we had to write an unhinged prompt… Initially when we launched the MCP, users constantly complained about \"Connection lost\" and stuff like that."
- url: https://supermemory.ai/blog/the-ux-and-technicalities-of-awesome-mcps/
- source_type: primary
- published: 2025-06-08
- confidence: high

### [7] Supermemory's own OpenClaw analysis (2026-02) catalogs tool-based agent memory failure modes: tool-mediated save/search uses more tokens not less, knowledge is not updated (redundant writes), and static file memory does not forget.
- quote: "The problem? Counterintuitively, this uses MORE, not LESS tokens - because the tool call etc are expensive too!… When saving new things to memory, it has no idea of what's already in there… This leads to it being a bit stupid when adding things, as it will add redundant information… It does not forget."
- url: https://supermemory.ai/blog/why-everyone-is-complaining-about-openclaws-memory-it-sucks-and-why-supermemory-fixes-it
- source_type: primary
- published: 2026-02-19
- confidence: high

### [8] Supermemory's cartesia SDK path had a silent memory-drop bug: plain-string search results were discarded in dedup so they never reached the agent prompt, and tool-call messages missing role/content raised KeyError instead of being skipped.
- quote: "plain-string search results are silently dropped… the entry never reaches the prompt… `get_last_user_message` raises `KeyError`… so a tool-call turn or provider event missing either key raised instead of being skipped."
- url: https://github.com/supermemoryai/supermemory/pull/1683
- source_type: primary
- published: 2026-09-18
- confidence: high

### [9] MiMo Desktop community issue #2426 documents a permission-gate failure: while a permission request is pending, newly sent chat commands look accepted but are silently dropped—never queued, executed, or cancelled with a notice.
- quote: "在权限请求仍处于 pending 状态时可以发送新的聊天指令，但该指令之后不会执行，也没有失败或取消提示… 因此从用户视角看，新指令实际上被静默丢弃了。"
- url: https://github.com/XiaomiMiMo/MiMo-Code/issues/2426
- source_type: primary
- published: 2026-09-18
- confidence: high

- quote: "MCP Token Trap: Why Your AI Agent Burns 35x More Tokens Than a CLI… Both Claude and OpenAi solved the mcp context bloat issue with on-demand tool discovery"
- url: https://hn.algolia.com/api/v1/search?query=MCP%20context%20bloat%20tools%20agents&hitsPerPage=10

- quote: "I got tired of telling my coding agent the same things over and over. I also didn't want to use a hosted memory service like supermemory, or run a local server like mem0. I wanted something small to store notes locally… keep all the data on my laptop."

## Dead ends
- GitHub HTML issue list pages (`github.com/.../issues?q=...`) returned transport errors; GitHub REST API and HN Algolia API worked.
- Reddit search and general websearch were unavailable in this environment (Web Search plugin not enabled); community coverage relies on HN Algolia + GitHub issues + Supermemory official blogs.
- Query `coding agent memory plugin failure` on HN Algolia returned almost nothing relevant (noise from unrelated posts).
- Query `supermemory MCP coding agent problems github issues` via websearch unavailable; GitHub issues API for supermemory monorepo is PR-heavy (product releases/docs), less community failure traffic than opencode-supermemory.
- MiMo-Code GitHub recent issues include permission/memory/desktop bugs but few explicit "plugin/MCP/skill" tagged reports in the top page; Plugins fields in issue templates are mostly empty.
- No high-comment HN thread dedicated solely to supermemory failure modes; SuperMemory-related HN posts are low-point Show/Ask HN with little discussion.
